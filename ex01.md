# [BÀI TẬP] THIẾT KẾ KIẾN TRÚC PHÂN RÃ (DECOMPOSITION & BOUNDED CONTEXTS)

---

## 1. Xác định Bounded Context và Ranh giới Service (DDD)

Áp dụng tư duy **Domain-Driven Design (DDD)** và nguyên tắc **Decomposition by Subdomain**, bài toán thương mại điện tử được phân rã thành 3 Bounded Contexts độc lập:

1. **Customer Context (`customer-service`):**
   * **Trách nhiệm:** Quản lý danh tính, hồ sơ khách hàng, thông tin đăng nhập và thông tin liên hệ.
   * **Cơ sở dữ liệu:** `customer_db` (PostgreSQL) - Sở hữu độc quyền.
2. **Product Context (`product-service`):**
   * **Trách nhiệm:** Quản lý danh mục hàng hóa, giá bán niêm yết, thông tin mô tả và số lượng tồn kho.
   * **Cơ sở dữ liệu:** `product_db` (PostgreSQL) - Sở hữu độc quyền.
3. **Order Context (`order-service`):**
   * **Trách nhiệm:** Quản lý vòng đời đơn hàng (tạo đơn, xác nhận, hủy đơn, trạng thái thanh toán) và lưu vết giá trị giao dịch.
   * **Cơ sở dữ liệu:** `order_db` (PostgreSQL) - Sở hữu độc quyền.

### Quy tắc bất biến trong kiến trúc:
* **Không dùng chung cơ sở dữ liệu:** Không có bất kỳ Foreign Key (FK) vật lý nào giữa bảng của service này sang bảng của service khác.
* **Không chia sẻ mã nguồn trực tiếp (No In-process dependency):** `OrderService` không phụ thuộc compile-time vào `Customer.java` hay `Product.java`. Giao tiếp giữa các service chỉ diễn ra qua giao thức mạng (HTTP REST / gRPC hoặc Message Queue).

## 2. Thiết kế chi tiết Thực thể (Entities) trong Spring Boot

### 2.1. Customer Service (`customer-service`)

* **Database:** `customer_db`
* **Entity:** `Customer`

```java
package com.ecommerce.customerservice.entity;

import jakarta.persistence.*;
import lombok.*;

@Entity
@Table(name = "customers")
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 100)
    private String fullName;

    @Column(name = "email", nullable = false, unique = true, length = 150)
    private String email;

    @Column(name = "password", nullable = false, length = 255)
    private String password; // Lưu trữ mật khẩu đã băm (BCrypt/Argon2)

    @Column(name = "address", length = 255)
    private String address;
}
```

### 2.2. Product Service (`product-service`)

* **Database:** `product_db`
* **Entity:** `Product`

```java
package com.ecommerce.productservice.entity;

import jakarta.persistence.*;
import lombok.*;
import java.math.BigDecimal;

@Entity
@Table(name = "products")
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false, length = 200)
    private String name;

    @Column(name = "price", nullable = false, precision = 15, scale = 2)
    private BigDecimal price; // Sử dụng BigDecimal để tránh sai số dấu phẩy động

    @Column(name = "stock_quantity", nullable = false)
    private Integer stockQuantity;

    @Column(name = "description", columnDefinition = "TEXT")
    private String description;
}
```

### 2.3. Order Service (`order-service`)

* **Database:** `order_db`
* **Entity:** `Order`

```java
package com.ecommerce.orderservice.entity;

import jakarta.persistence.*;
import lombok.*;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "orders") // Bắt buộc đặt name="orders" vì 'order' là từ khóa SQL
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Chỉ lưu ID tham chiếu đại diện cho Customer, KHÔNG quan hệ @ManyToOne
    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Column(name = "order_date", nullable = false, updatable = false)
    private Instant orderDate;

    @Column(name = "total_amount", nullable = false, precision = 15, scale = 2)
    private BigDecimal totalAmount;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 30)
    private OrderStatus status;

    @PrePersist
    protected void onCreate() {
        if (this.orderDate == null) {
            this.orderDate = Instant.now();
        }
    }
}
```

*Enum trạng thái đơn hàng (`OrderStatus.java`):*
```java
package com.ecommerce.orderservice.entity;

public enum OrderStatus {
    PENDING,
    CONFIRMED,
    SHIPPED,
    CANCELLED
}
```

## 4. Tại sao `Order` CHỈ NÊN LƯU `customerId` mà không lưu cả đối tượng `Customer`?

Trong kiến trúc Monolith truyền thống, lập trình viên thường dùng annotation `@ManyToOne private Customer customer;` để liên kết hai thực thể. Tuy nhiên, khi chuyển sang kiến trúc phân tán (Microservices & DDD), **việc lưu cả đối tượng `Customer` trong `Order` là một sai lầm nghiêm trọng**. 

`Order` chỉ được phép lưu thuộc tính tham chiếu định danh `Long customerId` vì các lý do cốt lõi sau:

### 4.1. Tôn trọng ranh giới Bounded Context & Tính tự chủ dữ liệu (Data Sovereignty)
* Trong ngữ cảnh đơn hàng (Order Context), mục tiêu nghiệp vụ là: *"Đơn hàng này thuộc về ai để thanh toán và giao nhận?"*.
* `Order Service` không sở hữu vòng đời của khách hàng. Nếu `Order` lưu nguyên đối tượng `Customer`, nó sẽ nắm giữ cả những thuộc tính không thuộc thẩm quyền của mình như: `password`, thông tin xác thực, tài khoản ngân hàng, v.v.
* **Vi phạm bảo mật & Nguyên tắc tối thiểu hóa dữ liệu (Data Minimization):** `Order Service` tuyệt đối không được phép biết hoặc lưu giữ hash mật khẩu (`password`) của khách hàng.

### 4.2. Khử triệt để phụ thuộc mã nguồn và Cơ sở dữ liệu (Decoupling)
* **Tầng Cơ sở dữ liệu:** `Order Service` kết nối vào `order_db`, còn dữ liệu `Customer` nằm ở `customer_db`. Một hệ quản trị cơ sở dữ liệu không thể tạo khóa ngoại liên database (Cross-Database Foreign Key) một cách an toàn và nhất quán.
* **Tầng Mã nguồn:** Nếu `Order` chứa `Customer`, dự án `order-service` buộc phải import class `Customer.java` từ một thư viện dùng chung (Shared Library/JAR). Khi `customer-service` thay đổi cấu trúc bảng hoặc thêm thuộc tính mới, `order-service` sẽ bị lỗi biên dịch (Compile-time error) hoặc buộc phải build lại toàn bộ. Sử dụng `customerId` giúp hai dự án hoàn toàn độc lập về vòng đời phát triển và triển khai.

### 4.3. Bảo toàn tính toàn vẹn lịch sử (Historical Immutability)
Đây là luận điểm nghiệp vụ quan trọng nhất:
* Khách hàng là một thực thể động (Dynamic Entity): Khách hàng có thể đổi tên, đổi email, đổi địa chỉ nhà sau 1 năm hoặc thậm chí yêu cầu xóa tài khoản.
* Đơn hàng là một bản ghi chứng từ kế toán trong quá khứ (Snapshot of Facts): Đơn hàng phản ánh sự kiện kinh tế đã diễn ra tại thời điểm đặt hàng.
* **Rủi ro nếu tham chiếu trực tiếp đối tượng:** Nếu `Order` tham chiếu trực tiếp đến `Customer`, khi khách hàng cập nhật địa chỉ từ Hà Nội sang TP.HCM, toàn bộ các đơn hàng đã giao thành công trong lịch sử 2 năm trước sẽ vô tình bị biến thành "giao đến TP.HCM" $\rightarrow$ Phá vỡ tính toàn vẹn của hồ sơ kế toán, thuế và lịch sử vận chuyển.
* *Cách giải quyết chuẩn:* `Order` chỉ lưu `customerId` để biết chủ tài khoản. Nếu cần lưu địa chỉ nhận hàng, `Order` sẽ lưu một bản chụp độc lập (Snapshot string) mang tên `shippingAddress` tại thời điểm bấm đặt hàng.

### 4.4. Tối ưu hóa hiệu năng & Băng thông (Performance & Serialization)
* Lưu trữ và truyền tải: Chỉ lưu một giá trị kiểu số nguyên (`Long customerId` - 8 bytes) thay vì tuần tự hóa (serialize) một đối tượng JSON cồng kềnh chứa đầy đủ các trường của Customer vào database hay payload đơn hàng.
* Tránh được lỗi tải dữ liệu lười biếng (`LazyInitializationException`) và vòng lặp tham chiếu đệ quy (`Infinite Recursion`) khi serialize JSON qua mạng.

## 5. Tổng kết

| Tiêu chí | Lưu cả đối tượng `Customer` (Kiểu cũ / Monolith) | Chỉ lưu `customerId` (Kiểu DDD / Microservices) |
| :--- | :--- | :--- |
| **Tính độc lập** | Phụ thuộc chặt chẽ (Tight Coupling). | Phân rã hoàn toàn (Loose Coupling). |
| **Cơ sở dữ liệu** | Bắt buộc chung Database / Schema. | Database per Service (Tách biệt vật lý). |
| **Bảo mật** | Nguy cơ rò rỉ thông tin nhạy cảm (`password`). | Bảo vệ dữ liệu, chỉ truyền ID khi cần thiết. |
| **Lịch sử đơn hàng** | Dễ bị sai lệch số liệu khi khách hàng cập nhật profile. | Bất biến, bảo vệ chứng từ giao dịch. |
| **Khả năng mở rộng** | Kém; khó nâng cấp và deploy độc lập. | Tối ưu; mỗi service tự do mở rộng quy mô. |
